# SkyMessage на VPS

Ставится рядом с другими проектами на том же сервере и ничего у них не трогает:

- всё лежит в `~/skymessage` и работает как отдельный Docker Compose проект `skymessage`, со своей сетью
  `172.30.80.0/24`, своими томами и своей базой PostgreSQL;
- порты 80 и 443 сервера не используются (их держит другой проект за Cloudflare). Мессенджер доступен напрямую по
  `https://chat.skye.estate:8443`: запись в DNS без проксирования Cloudflare, потому что Cloudflare в России режут;
- наружу открыты только 8443 (HTTPS), 7881/tcp и 7882/udp (звонки). API, база и сигналинг LiveKit во внутренней сети;
- у контейнеров ограничены память и процессор, а FFmpeg обрабатывает по одному видео за раз;
- HTTPS-сертификат выпускает Caddy через DNS-проверку Cloudflare (токен с правом Zone → DNS → Edit лежит в
  `~/skymessage/cloudflare.env`).

## Обновление

```bash
deploy/vps/deploy.sh
```

Скрипт публикует API с веб-клиентом на этом компьютере, заливает файлы через rsync (только изменения) и
пересобирает лёгкий образ на сервере. Компиляции на сервере нет. Обычно его запускает CI при каждом релизе (ниже);
вручную — для первого развёртывания или если CI недоступен.

## Секреты и бэкапы

`~/skymessage/.env` создаётся при первом развёртывании (`init-env.sh`) и больше не меняется. **Сохрани его копию
в надёжном месте**: `STORAGE_MASTER_KEY` расшифровывает все фото, видео и файлы, без него бэкапы бесполезны.
Там же лежит код приглашения для регистрации (`REGISTRATION_CODE`).

Бэкап базы делается каждый день в 04:17 (crontab пользователя, `backup.sh`), хранятся три последних дампа в
`~/skymessage/backups`. Это копии на том же сервере: для настоящей защиты их стоит периодически скачивать.

## Откат

```bash
ssh -i ~/.ssh/skymessage_vps -p 22345 JasperMaglot@77.73.131.184 'cd ~/skymessage && docker compose down'
```

Остальные проекты на сервере это не затрагивает. Данные остаются в томах `skymessage_*`.

## CI, релизы и автообновление

### Как это устроено

- Ветки: фичи в `feature/*` → `develop` → `main`. Любой пуш и pull request запускает CI
  (`.github/workflows/ci.yml`): сервер и веб-клиент собираются без предупреждений, проходят юнит-тесты, тесты
  клиентского ядра и интеграционные тесты (PostgreSQL в Docker), и проверяется, что собирается Android-приложение.
- **Пуш в `main` — это релиз** (`.github/workflows/release.yml`), по шагам:
  1. весь CI; если что-то упало, дальше ничего не происходит;
  2. номер релиза = число коммитов в `main`: версия `0.2.<n>`, Android versionCode `<n>`. Поэтому историю `main`
     никогда не переписывают (никаких force-push и «squash» старых коммитов), иначе номер уменьшится и телефоны
     перестанут обновляться;
  3. собирается подписанный APK (ключ из секретов, сервер по умолчанию `https://chat.skye.estate:8443/`),
     проверяются подпись и versionCode, пишется манифест `latest.json` (версия, SHA-256, размер);
  4. APK уходит на сервер в `~/skymessage/updates` (`publish-update.sh --stage`): под временным именем, с
     проверкой SHA-256 уже на сервере. Манифест пока лежит рядом как `staged-<n>.json` — телефонам его ещё не
     предлагают. Хранятся три последних APK;
  5. сервер и веб-клиент разворачиваются тем же `deploy.sh`, и сразу после запуска нового сервера манифест
     становится `latest.json` (прежний остаётся как `latest.json.prev`). Так старый сервер никогда не предлагает
     приложение, собранное для нового;
  6. проверка: `https://chat.skye.estate:8443/api/app/version` отвечает новой версией;
  7. если любой из шагов 4–6 упал, релиз отзывается (`publish-update.sh --withdraw`): телефонам снова предлагается
     прежняя версия, а на сервере остаётся то, что успело развернуться.
- **Телефоны** спрашивают сервер при запуске, при возвращении в приложение (не чаще раза в час), каждые несколько
  часов и сразу после переподключения — а деплой перезапускает сервер, поэтому новая версия замечается за минуту.
  APK скачивается в фоне (докачивается после обрыва; с «Загружать только по Wi‑Fi» — только по Wi‑Fi), проверяются
  размер и SHA-256. На Android 12+ после одного разрешения «Установка неизвестных приложений» обновление ставится
  само, пока приложением не пользуются (не во время звонка). На Android 8–11 Android один раз спрашивает «Обновить
  приложение?» — в списке чатов появляется карточка «Обновление готово». Настройки: «Настройки → О приложении →
  Обновления» (проверить сейчас, «Обновлять автоматически», «Загружать только по Wi‑Fi»).
- **Веб-версия**: открытая страница замечает, что сервер теперь отдаёт новую версию; если вкладка скрыта, она
  перезагружается сама, иначе показывает карточку «Вышла новая версия» с кнопкой «Обновить».
- Пока секреты не заданы, релизные шаги пропускаются: запуск остаётся зелёным, в нём уведомление «Release skipped»
  со списком недостающих секретов.

### Секреты GitHub

Репозиторий на GitHub → **Settings → Secrets and variables → Actions → вкладка Secrets → New repository secret**.
Имя — как в таблице, значение — вставить целиком (многострочные тоже). Значения потом не видны даже владельцу,
их можно только заменить.

| Секрет | Что положить |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | keystore для подписи APK в base64: `base64 -i skymessage-release.keystore \| pbcopy` (macOS) или `base64 -w0 skymessage-release.keystore` (Linux) |
| `ANDROID_KEYSTORE_PASSWORD` | пароль keystore |
| `ANDROID_KEY_ALIAS` | alias ключа в keystore (например `skymessage`) |
| `ANDROID_KEY_PASSWORD` | пароль ключа (часто совпадает с паролем keystore) |
| `VPS_SSH_KEY` | приватный SSH-ключ для деплоя — весь файл, от `-----BEGIN` до `-----END` |
| `VPS_HOST` | адрес сервера: `77.73.131.184` |
| `VPS_PORT` | SSH-порт: `22345` |
| `VPS_USER` | пользователь на сервере: `JasperMaglot` |
| `VPS_KNOWN_HOSTS` | отпечаток сервера, вывод `ssh-keyscan -p 22345 77.73.131.184` (защита от подмены сервера) |

Необязательные **переменные** (там же, вкладка Variables): `SKY_SERVER_URL` — сервер, зашитый в APK по
умолчанию (`https://chat.skye.estate:8443/`); `ANDROID_MIN_VERSION_CODE` — сборки ниже этого номера обязаны
обновиться (по умолчанию 0; поднимать, только когда новый сервер ломает старые приложения).

**Ключ подписи — важно.** Android ставит обновление только поверх приложения, подписанного тем же ключом.
Если у тебя уже есть keystore, которым подписаны APK на телефонах, — используй его. Новый создаётся так:

```bash
keytool -genkeypair -v -keystore skymessage-release.keystore -alias skymessage -keyalg RSA -keysize 4096 -validity 36500
```

Храни keystore и пароли в надёжном месте (не в репозитории): без них телефоны смогут обновиться только
переустановкой. Если на телефонах стоит сборка с другим ключом (например, debug-сборка с компьютера), первое
автообновление не встанет: карточка скажет, что версия подписана другим ключом, и даст ссылку. Тогда один раз:
удалить SkyMessage и поставить по ссылке `https://chat.skye.estate:8443/updates/latest.apk` (сообщения хранятся на
сервере, нужно только войти заново). Дальше всё обновляется само.

### Сервер (один раз)

- Отдельный ключ для CI: `ssh-keygen -t ed25519 -f skymessage_ci -C skymessage-ci -N ""`. `skymessage_ci.pub`
  дописать в `~/.ssh/authorized_keys` пользователя `JasperMaglot` на VPS, содержимое `skymessage_ci` — в секрет
  `VPS_SSH_KEY`, сам файл после этого удалить. У пользователя должен быть доступ к Docker (как и для ручного
  `deploy.sh`).
- `ssh-keyscan -p 22345 77.73.131.184` — сверить отпечаток с тем, что показывает `ssh` при входе, и положить вывод
  в `VPS_KNOWN_HOSTS`.
- Каталог `~/skymessage/updates` скрипты создают сами; в контейнер API он подключён только для чтения
  (`Updates__Path=/updates`). Через HTTPS отдаются только файлы `*.apk`, манифест читает сам API.

Что CI делает на сервере — только внутри `~/skymessage` и compose-проекта `skymessage`: rsync файлов,
`docker compose build` и `docker compose up -d` своих сервисов, удаление своего же прежнего образа API.
Другие контейнеры, Caddy на 80/443, файрвол и сам Docker не трогаются: никаких `prune`, перезапусков Docker или
сервера. Caddy проекта пересобирается только если его бинарника на сервере нет.

### Выпуск релиза

1. Фичи сливаются в `develop` (CI зелёный).
2. Когда владелец согласен — pull request `develop` → `main` и merge.
3. GitHub → **Actions → Release** — видно, как идут шаги; примерно через 20–30 минут сервер обновлён, APK опубликован.
4. Телефоны обновятся сами в ближайшие минуты (в фоне — когда приложением не пользуются), веб-страницы — при
   следующем скрытии вкладки или по кнопке «Обновить».

Повторить релиз того же коммита: Actions → Release → **Run workflow** (номер тот же, телефоны ничего не скачивают
заново). Первая установка на новый телефон — ссылка `https://chat.skye.estate:8443/updates/latest.apk`.

**Откат.** Android не ставит версию с меньшим номером, поэтому откат — это новый релиз: `git revert` проблемного
коммита в `develop` и merge в `main`. Сервер в крайнем случае можно вернуть вручную: `deploy.sh` из нужного коммита.
Перестать предлагать телефонам последнюю версию (те, что уже обновились, на ней и останутся):
`deploy/vps/publish-update.sh --withdraw dist/latest.json` с манифестом этого релиза (он есть в артефакте
`android-release` запуска Release).

**APK вручную, без CI** (собран с `-p:SkyMessageBuildNumber=<n>`, где `<n>` больше текущего номера; без `--stage`
манифест предлагается телефонам сразу, поэтому сервер для этой версии должен уже работать):

```bash
python3 -I deploy/vps/release-manifest.py --apk dist/SkyMessage-0.2.<n>.apk --version-code <n> \
    --version-name 0.2.<n> --out dist/latest.json
deploy/vps/publish-update.sh dist/SkyMessage-0.2.<n>.apk dist/latest.json
```
